# Challenge 1 — native generated-code diagnostic

## What Refit does

An owner starts a managed agent migration in the existing workspace, supplies independent training, validation and holdout cases, and authorizes the migration's Vultr inference budget. After the migration ends, the owner may select **Run diagnostic** in that run's header. The UI does not accept Python, a custom model identifier or free-form diagnostic prompts.

The trusted server builds a bounded, **sanitized projection of the persisted, measured** `source_training` and `target_training` phases. The diagnostic never changes an export decision: the original application acceptance and fresh export checks remain authoritative.

The host makes **one** call to `deepseek-v4.1-flash-1017` through Vultr Serverless Inference to generate Python source from this projection. The source runs under `DockerSandbox(runtime="runsc")` inside a fresh disposable gVisor container on the Vultr host. The host then runs **the same model-written code** in a second fresh gVisor worker against a privately generated synthetic arithmetic case not sent to the coding model. The trusted Python oracle recomputes both expected outputs. Both tests must return matching JSON and prove container creation, exit success, a valid event hash chain and verified removal.

The resulting `run.diagnostic` is persisted under the owning run in the existing durable store. The run's **Evidence → Generated diagnostics** inspector presents model identity, source code, output, independent expectation, cross-check, configured sandbox limits, runtime identity and cleanup receipts. The public, signed-out workspace remains a **recorded read-only preview**, not an anonymous live code-execution service.

## Access and quotas

- Only authenticated owners of completed migrations can request diagnostics. Valid origin and session checks apply. A separately provisioned, expiring reviewer pass is owner-scoped to exactly one migration and may run exactly one diagnostic within its fixed 16-request budget (at most 15 migration requests plus one reserved diagnostic request). Reviewer requests use an explicitly provisioned budget separate from ordinary signups; they cannot create arbitrary additional runs.
- Requires `REFIT_ENABLE_SANDBOX_DIAGNOSTICS=1` and `REFIT_SANDBOX_RUNTIME=runsc`. No automatic fallback to runc.
- At most one diagnostic attempt per migration, exactly one authorized Vultr request, one concurrent diagnostic, one reserved account/global request budget; interrupted attempts remain charged and are never retried automatically.
- Runtime failure, a mismatched oracle, missing/false cleanup receipt or unverified gVisor identity **cannot** produce a verified diagnostic.
- No user-supplied code is accepted at the HTTP boundary. The only agent-written program is generated by the trusted Vultr inference broker using the fixed diagnostic contract.
- Worker has no Docker socket, secrets, network, privilege or writable root; UID 65534, caps dropped, no-new-privileges, tmpfs, CPU/memory/PID/output/wall-time limits. No inference key crosses the worker boundary.
- Production uses an owner-private \`/var/lib/refit-application/sandbox-staging\` bind source, visible to the Docker daemon but not served to users. \`PrivateTmp=true\` remains enforced on the controller service. The fix addresses a genuine first production run that failed before container creation because the daemon could not see a \`/tmp\` path from the service's private mount namespace.

## Controlled containment evidence

On a Docker-capable gVisor host, run:

```bash
python3 -m scripts.c1_acceptance --output /var/lib/refit/evidence/c1-containment.json
```

The **static synthetic containment probe** attempts to read a synthetic host-only canary, connect externally and write a protected root path. An independent timeout worker tests wall-clock enforcement. The host checks the canary remains unchanged and both disposable workers are removed. It is deliberately labelled *not AI-generated*, so it is not confused with the live model-written diagnostic.

For real inference in the deployed web application, sign in, open a completed migration with actual training observations, select Run diagnostic, and inspect the generated code and both gVisor receipts in Evidence. Save the private owner-scoped `/api/application/runs/<id>/evidence` response after verification for adjudication, sanitizing private data before any public release.

## Exact responsibility boundaries

| Challenge requirement | Refit implementation |
| --- | --- |
| User starts a meaningful task | Account-owned migration, then a bounded diagnosis on measured results |
| Agent code generation | One real Vultr Serverless Inference request via trusted broker |
| Isolated execution on Vultr | Two fresh `runsc` Python workers launched by the Vultr-host controller |
| Real effects | Worker stdout, stderr, exit status, runtime identity, file/input/code hashes, execution and cleanup ledgers |
| Independent verification | Protected score oracle plus unseen synthetic second execution, outside the generated code |
| Durable, inspectable evidence | Owner-scoped run record and existing Evidence inspector |
| Cleanup & containment | Runner's forced remove/inspect receipts and separate synthetic containment acceptance |
| Judge access | Public recorded workspace, account-gated live migration and diagnostic |

## Limits that must remain explicit

1. The generated program summarizes **training evidence**; it is **not** the migration's independent business oracle and cannot unlock a withheld export.
2. The current managed application importer supports a defined Python/Node contract; Refit does not claim arbitrary-agent compatibility.
3. The application service now runs **without Docker-group membership**. A separate root-owned broker validates UID, exact `runsc` commands, content-addressed images and private staging paths before launching a worker. Host Docker access remains privileged inside this narrow trusted broker; neither the application service nor generated code receives the unrestricted Docker socket. [Real Vultr broker/containment acceptance](https://github.com/Davemafy/refit/actions/runs/42484161419).
4. gVisor does not provide a distinct host kernel; the signed binary, registration, container runtime, worker policy and actual observed denial must be checked on the **Vultr VM**, not inferred from Github CI.
5. Bounded workers have enforced timeouts; an additional UI cancellation action for a running diagnostic is not yet provided. Each invocation is single-use.
6. The image is deployed via a trusted `python:3.11-alpine` tag pull, not a supplied immutable digest; image pinning and provenance hardening are follow-ups.
7. No claim of deployed Challenge 1 compliance is justified without matching live production SHA, a real user-triggered Vultr inference response, executed generated Python, independent observed outputs, valid cleanup receipts and browser evidence.
8. The current public entry point is IP-based HTTPS and the recorded public preview does not itself offer anonymous execution.
